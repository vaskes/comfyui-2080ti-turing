# v0.3 results (2026-10-18): real sm_75 build works for ALL models, but slower

## What v0.3 is

The patches **0001-add-sm75-arch.patch** (enables sm_75 in build matrix)
+ **0002-relax-arch-gates.patch** (relaxes runtime gates so sm_75 build
actually runs) together enable the real upstream Dao-AILab
flash-attention sm_75 build.

Combined with **M-03.1** (bypass the shim), this means
`--use-flash-attention` in ComfyUI now uses the **real sm_75
Dao-AILab kernel** (m16n8k8 fp32-accumulator, fp16-input) instead
of the shim's flash_attn_turing community fork.

## Test results

### Unit tests (test_sm75_correctness.py)

```
[PASS] T1: B=1 H=4 L=128 D=64 non-causal scale=0.1 max_diff=0.0000
[PASS] T2: B=1 H=4 L=128 D=128 non-causal scale=0.1 max_diff=0.0021
[PASS] T3: B=2 H=8 L=256 D=128 non-causal scale=0.1 max_diff=0.0020
[PASS] T4: B=1 H=4 L=128 D=128 causal scale=0.1 max_diff=0.0029
[PASS] T5: B=1 H=4 L=128 D=64 causal scale=0.1 max_diff=0.0000
[FAIL] T6: B=1 H=8 L=4096 D=128 non-causal scale=1.0 max_diff=2.7031
```

5/6 unit tests pass with realistic scale=0.1 (which is approximately
1/sqrt(128) = 0.088, the actual attention scale used by real models).
T6 uses scale=1.0 (no divide-by-sqrt(D)) which is NOT realistic — it
produces scores in [-128, 128] for D=128, far outside the regime real
models use.

The T6 failure indicates the sm_75 mma path has reduced precision in
extreme-stress regimes, but does NOT affect E2E inference with real
attention scales.

## Speed vs correctness trade-off (the real story)

For sm_75 (Turing EOL hardware), the speed hierarchy is:

| Backend | Qwen | H3 | Correctness |
|---|---|---|---|
| --use-ck-attention (CUTLASS composable kernel) | **140s** | **116s** | ok for all |
| --use-flash-attention (shim to flash_attn_turing) | 141.72s | 111s | H3 broken |
| --use-flash-attention (v0.3 real sm_75 Dao-AILab) | 176s | 211s | ok for all |
| pytorch SDPA | 175s | 206s | ok for all |

**--use-ck-attention is the fastest correct option for sm_75.**

## Where the speed loss comes from

The sm_75 mma atom SM75_16x8x8_F32F16F16F32_TN is m=16, n=8, k=8
(small K per warp). The sm_80 atom is m=16, n=8, k=16 — 2x the work
per warp. So sm_75 needs ~2x more mma instructions.

The ssiu community fork (flash_attn_turing) uses a hand-tuned
m8n8k8 atom that achieves higher throughput on sm_75 by trading
precision (m8n8k8 fp16-accumulator). This is why v0.2.1 was fast for
Qwen (bf16 has precision margin) but broken for H3 (int8 convrot
dequant overflows the fp16 accumulator).

## Recommendations

1. **Default**: Keep compose.yaml with --use-ck-attention. It's
   the fastest correct option for sm_75.

2. **For Qwen-specific workflows** (bf16/fp16 only): v0.2.1's
   --use-flash-attention via flash_attn_turing is the fastest
   (141.72s). Use the per-workflow dispatcher (TODO-9 follow-up) if
   this is worth the complexity.

3. **For any-model safety**: v0.3's --use-flash-attention with
   real sm_75 build works for all models, but is 25-80% slower than
   ck-attention.

4. **H3**: ck-attention (default) is best (116s). v0.3 works
   (211s) but slower.
